# Technical Architecture

## 1. High-level architecture

```text
React UI
  ├── Architecture Editor (@xyflow/react)
  ├── Resource Inspector (React Hook Form + Zod)
  ├── Learn / Troubleshoot / Exam modes
  └── Progress Dashboard
        |
        v
Typed API client
        |
        v
FastAPI
  ├── Project API
  ├── Architecture API
  ├── Simulation API
  ├── Lab API
  ├── Question API
  └── Progress API
        |
        v
Application services
  ├── Resource registry
  ├── Schema validation
  ├── Relationship validation
  ├── Simulation orchestrator
  │     ├── Network evaluator
  │     ├── IAM/S3 policy evaluator (limited subset)
  │     └── Fault/scenario engine
  ├── Lab scoring
  └── Exam scoring
        |
        v
Repository layer
  └── SQLite (MVP), PostgreSQL-compatible abstractions later
```

## 2. Recommended stack
### Frontend
- React + TypeScript + Vite
- `@xyflow/react` for graph canvas
- Zustand for editor and session state
- React Hook Form + Zod for forms
- Vitest + React Testing Library
- Optional ELK.js later for auto-layout

### Backend
- Python + FastAPI
- Pydantic models for request/response validation
- SQLAlchemy 2.x or SQLModel; choose one and use consistently
- Alembic migrations if SQLAlchemy is selected
- Pytest
- Ruff for lint/formatting and mypy or pyright if practical

### Persistence
- SQLite for initial local MVP.
- Store graph node/edge data as versioned JSON alongside normalized learning records.
- Hide persistence behind repositories to make later PostgreSQL migration manageable.
- Do not add Redis or background workers in MVP.

## 3. Module boundaries
### Editor
Owns visual state and user interaction only. It must not contain AWS behavior rules.

### Resource registry
Defines resource types, config schemas, allowed relationship types, ports/handles, validation rules, and supported simulation capabilities.

### Validation engine
Checks schema, required properties, relationship legality, dependencies, and known invalid combinations.

### Simulation engine
Consumes an immutable architecture snapshot plus a simulation request and optional deterministic seed. Returns a trace and summary. It must not mutate the source architecture.

### Fault engine
Applies a named fault to a copied scenario state, records the change, and supports reset/replay. A fault must declare preconditions and expected symptoms.

### Learning engine
Stores objectives, labs, checkpoints, hints, scoring rubrics, and learner attempts. It may call validation/simulation services but must not reimplement their rules.

### Exam engine
Scores original questions and stores attempts. It is independent from architecture simulation.

## 4. Resource model
Use stable resource IDs generated by the app, not AWS IDs. Each node includes:
- `id`
- `type`
- `label`
- `config`
- `position`
- `parentId` where applicable
- `metadata` for versioned editor-specific properties

Each edge includes:
- `id`
- `source`
- `target`
- `relationType`
- optional `sourceHandle`, `targetHandle`, and `metadata`

Relationship types must be typed. Do not treat every edge as network connectivity.

## 5. Simulation contract
Input:
- architecture snapshot/version;
- simulation type;
- source and destination resource IDs where relevant;
- scenario state/fault IDs;
- engine version.

Output:
- run ID;
- snapshot hash or version;
- overall status;
- ordered trace steps;
- rule IDs;
- affected resources;
- messages and remediation hints;
- unsupported checks encountered;
- timestamps/duration for UI only (not used to claim real AWS latency).

Statuses:
- `PASS`
- `FAIL`
- `WARN`
- `DEGRADED`
- `UNSUPPORTED`

The same architecture snapshot, simulation request, engine version, and seed should produce the same semantic result.

## 6. Persistence and versioning
- Architecture documents include `schemaVersion`.
- Simulation runs reference an immutable snapshot.
- Labs and questions include content versions.
- Migrations must preserve existing user projects.
- Export format should be documented JSON and should not contain secrets.

## 7. Security and privacy
- No AWS credentials stored in MVP.
- No external network calls required for core use.
- Validate imported JSON size, schema, node count, and edge references.
- Do not execute code or shell commands from imported projects.
- Treat question and lab content as data, never executable instructions.
- If real AWS integration is added later, isolate it behind a separate opt-in adapter and require cost and cleanup safeguards.

## 8. Key architectural decisions
- Rule-based simulation before AI.
- No graph database for MVP.
- No microservices; use a modular monolith.
- No exact AWS parity claim.
- Simulation logic stays testable without React or database.
